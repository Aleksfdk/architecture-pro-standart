| F | Функциональные (Functionality) | |
| F1 | Сайт показывает новому клиенту список депозитов с актуальными ставками. | Сейчас ставка есть только в Excel и раз в день уходит почтой. Каталог на сайте не из чего собрать, пока у ставки нет системного источника. |
| F2 | На сайте клиент оставляет заявку на депозит: телефон и Ф. И. О. | Это заявка нового человека, а не открытие депозита. После звонка клиент приходит в отделение на идентификацию. |
| F3 | Заявка с сайта доступна менеджеру в системе кол-центра. Менеджер звонит клиенту и может предложить особые условия. | Особые условия по-прежнему согласует бэк-офис. Кол-центр должен видеть и саму заявку, и уже согласованную ставку. |
| F4 | В интернет-банке клиент видит депозиты с актуальными ставками и персональную ставку для себя. | Персональная ставка считается по данным клиента. Читать её при каждом открытии страницы прямым запросом в базу АБС нельзя: база и так перегружена. |
| F5 | В интернет-банке клиент указывает счёт и сумму, подаёт заявку на депозит и подтверждает операцию СМС-кодом. | |
| F6 | На MVP менеджер бэк-офиса обрабатывает заявку и подтверждает условия депозита в АБС. | Автоматическое открытие без сотрудника в этот этап не входит. |
| F7 | Клиент получает СМС после подтверждения ставки и отдельное СМС после открытия депозита. | Отправку выполняет существующий СМС-шлюз банка через телеком-оператора. |
| F8 | Сотрудники депозитного и кредитного бэк-офиса ведут ставки и согласуют ставку по заявке в системе, а не в Excel и по почте. | Бизнес предлагает разместить это в АБС: подтверждение условий на MVP и так делает менеджер в АБС. Запись в базу АБС напрямую из интернет-банка при этом недопустима. |
| F9 | Сайт показывает новому клиенту предложение кредита со ставкой. Полный набор условий хранится в кредитном конвейере. | Сайт не заводит вторую копию продуктовых условий. |
| F10 | На сайте заявка на кредит подаётся с телефоном и Ф. И. О. Если клиент заполнил паспортные данные, он сразу получает решение: одобрено или отказано. | Клиент для банка новый, истории в АБС нет. Скоринг может опереться только на общие данные бюро кредитных историй. |
| F11 | После заявки на кредит с сайта клиенту уходит СМС с приглашением в отделение для идентификации и получения кредита. | |
| F12 | В отделении менеджер подаёт заявку на кредит через АБС. Если клиент уже получил предварительное решение на сайте, сотрудник продолжает ту же заявку. Если заявки не было, создаёт новую. | Заявка должна быть в отделении в тот же день. Суточная выгрузка из АБС в конвейер этого не обеспечивает, а делать обмен чаще нельзя. |
| F13 | В интернет-банке клиент видит кредиты с актуальными условиями, как на сайте, и предодобренное предложение с рассчитанной суммой, если скоринг по нему уже был. | Предодобренная сумма берётся из уже выполненного скоринга, а не из нового пакетного пересчёта. |
| F14 | В интернет-банке клиент указывает счёт зачисления и данные заявки, отправляет заявку на кредит и подтверждает её СМС-кодом. | |
| F15 | Если к моменту заявки ситуация клиента изменилась, скоринг повторяется по упрощённой процедуре. Такие заявки сотрудники обрабатывают быстрее и в течение того же рабочего дня. | Быстрый путь нельзя построить на обмене баз АБС и конвейера: он идёт раз в сутки, и учащать его нельзя. |
| F16 | При изменении статуса кредитной заявки клиент получает СМС. | |
| F17 | Дополнительно. У заявки один идентификатор на сайте, в интернет-банке, в кол-центре, в АБС и в кредитном конвейере. | Без общего идентификатора отделение не отличит уже созданную заявку от новой, а кол-центр не привяжет особые условия к обращению с сайта. |
| F18 | Дополнительно. Депозитный и кредитный бэк-офис ведут ставки, но не видят клиентские данные друг друга. | Так разделён текущий процесс по требованиям безопасности. Общий справочник ставок не должен открыть кредитному сотруднику депозитный контур и наоборот. |
| F19 | Трафик сайта и интернет-банка шифруется при передаче телефона, Ф. И. О., паспортных данных, счёта и суммы. | Это прямое требование к чувствительным данным с сайта и из интернет-банка. Паспорт до визита в отделение у банка ещё нигде не хранится. |
| U | Удобство использования (Usability) | |
| U1 | Сайт и интернет-банк следуют дизайн-системе банка: привычные цвета и брендированные элементы. | |
| U2 | Заявка на сайте состоит из телефона и Ф. И. О. Паспортные данные клиент заполняет только если хочет решение по кредиту сразу. | Короткий сценарий и есть ожидаемое удобство. Отдельная полная анкета на сайте новым клиентам не нужна. |
| U3 | Дополнительно. Сразу после отправки заявки клиент видит следующий шаг: звонок кол-центра, визит в отделение или решение по кредиту. | Иначе пауза до СМС выглядит как потеря заявки. Каналу нужен статус заявки, а не только факт отправки формы. |
| R | Надёжность (Reliability) | |
| R1 | Сайт, интернет-банк, кол-центр, кредитный конвейер и скоринг работают круглосуточно и доступны 99,9% времени. | |
| R2 | При отказе одного ЦОД интернет-банк остаётся доступен и выдерживает свою нагрузку. | Сейчас интернет-банк работает на одной группе серверов в одном ЦОД, на резервный ЦОД переключаются вручную. Команда интернет-банка считает 99,9% на текущей платформе недостижимым: клиентов мало, и простой в течение дня для банка терпим. Требование остаётся целевым, текущая схема его не закрывает. |
| R3 | Поток онлайн-заявок не нарушает работу АБС. Интернет-банк в новом процессе не обращается к API АБС напрямую. | База АБС уже перегружена. Действующая интеграция интернет-банка устроена ещё жёстче: это прямой доступ к базе АБС. Для депозитов и кредитов такой способ не повторяем. |
| R4 | Кредитный конвейер и скоринг сохраняют работу 24/7 и горизонтальное масштабирование. | Оба решения уже рассчитаны на рост нагрузки. Новый канал не переводит их на суточную пачку из АБС. |
| R5 | Дополнительно. Сбой или задержка СМС не отменяет принятую заявку и не стирает решение по ней. | Между банком и клиентом стоят СМС-шлюз и внешний телеком-оператор. Статус хранится в системах банка и не зависит от доставки сообщения. |
| R6 | Сайт, интернет-банк и новые сервисы масштабируются горизонтально. Запросы распределяются между серверами, экземплярами приложений и ЦОД. | АБС в эту схему не входит: её база позволяет только вертикальный рост. |
| P | Производительность (Performance) | |
| P1 | Клиентские операции на сайте и в интернет-банке отвечают за миллисекунды. | |
| P2 | Справочные данные клиентской операции отдаются быстрее чем за секунду. | При платежах часть справочников сейчас грузится дольше секунды. Каталоги депозитов и кредитов со ставками не должны работать так же. |
| P3 | Решение новому клиенту на сайте, который ввёл паспорт, возвращается в рамках этого же обращения. | Скоринг в рабочие часы и так под нагрузкой. Отдельный контур предрасчётов на него не добавляется. Онлайн-вызов допустим в момент настоящей заявки. |
| P4 | Сотрудники обрабатывают заявки по предодобренным предложениям в тот же рабочий день. | Это срок бизнес-обработки. Ускорение обмена баз АБС и конвейера для него недоступно. |
| S | Поддерживаемость (Supportability) | |
| S1 | Новые компоненты собираются из технологий, которые банк уже сопровождает: MS SQL, Oracle, .NET, Java, Python, PHP, React. | Другую технологию можно взять, если она совместима с текущими платформами и в банке есть люди, которые знают хотя бы её язык. Java есть у команды АБС и у конвейера, Python есть у скоринга, .NET есть у интернет-банка. |
| S2 | Открытие депозита можно вынести в отдельный сервис. Остальной монолит интернет-банка не переписывается. | Монолит на ASP.NET MVC 4.5 и .NET Framework 4.5, обновление ядра зависит от подрядчика. Kafka этой платформой не поддерживается, хотя как очередь на перспективу она предпочтительна. Отдельный сервис может работать с очередью, не таща за собой весь интернет-банк. |
| S3 | По депозитному и кредитному сценарию есть документация, достаточная для следующего расширения без чтения кода монолита. | Прямой запрос бизнеса к дальнейшему развитию. |
| S4 | Дополнительно. Смена ставки не требует выпуска новой версии сайта или интернет-банка. | Базовая ставка обновляется каждый день, персональная считается по клиенту. Ежедневный релиз каналов сделает изменение ставки длиннее текущего письма с Excel. |
| +R | + Ограничения (Restrictions) | |
| +R1 | На MVP депозит открывается только после подтверждения менеджера бэк-офиса в АБС. | Автоматическое открытие без сотрудника относится к целевому состоянию через год, не к этому этапу. |
| +R2 | Банк не принимает нового клиента без личной проверки документов в отделении. | Поэтому сайт завершается заявкой и визитом, а не открытым счётом. |
| +R3 | Ядро интернет-банка силами подрядчика для сценария СМС не дорабатывается. | Работа с СМС уже есть в ядре, но изменение ядра привязано к подрядчику. СМС-код и СМС-уведомления команда банка делает в своём контуре. |
| +R4 | Текущая платформа интернет-банка несовместима с Kafka. | Если очереди нужны, Kafka остаётся предпочтительным выбором на перспективу, но встроить её в монолит .NET Framework 4.5 нельзя. |
| +R5 | АБС масштабируется только вертикально. | Ограничение базы Oracle. Горизонтальное распределение нагрузки относится к каналам и новым сервисам. |
| +R6 | Обмен между базами АБС и кредитного конвейера нельзя ускорить и нельзя выполнять чаще одного раза в сутки. | Онлайн-заявка, предодобренный кредит и продолжение заявки в отделении на эту интеграцию не опираются. |
| +R7 | На скоринг нельзя добавлять предрасчёты сверх уже существующей нагрузки. | В рабочие часы система и так занята. Повторный скоринг по заявке допустим только по упрощённой процедуре, когда данные клиента изменились. |
| +R8 | Дополнительно. Паспортные данные с сайта не сохраняются прямым доступом в базу АБС. | До идентификации это ещё не клиент банка, а база АБС перегружена. Данные паспорта живут рядом с заявкой и вызовом скоринга. |
