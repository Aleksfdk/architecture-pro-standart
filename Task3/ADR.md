### **Нефункциональные требования**

| **№** | **Требование** |
| :-: | :- |
| N1 | Сайт и интернет-банк в новом процессе не обращаются к API и базе АБС. Заявки не создают синхронную нагрузку на Oracle. |
| N2 | Каталог и персональная ставка отвечают из витрины сервиса за миллисекунды. Справочник ставок отдаётся быстрее чем за секунду. |
| N3 | Канал принимает заявку круглосуточно. Сервис депозитов масштабируется горизонтально, АБС только вертикально. |
| N4 | Трафик сайта и интернет-банка с телефоном, Ф. И. О., счётом и суммой шифруется. Форма сайта уходит в сервис через backend сайта. |
| N5 | СМС-код и тексты уведомлений делает команда банка. Ядро монолита подрядчик для этого не меняет. |
| N6 | Очередь между каналом и АБС строится на Kafka. В монолит .NET Framework 4.5 Kafka не встраивается. |
| N7 | Сбой СМС не удаляет заявку и не отменяет подтверждение в АБС. |
| N8 | Депозитный и кредитный бэк-офис не видят клиентские данные друг друга. |
| N9 | Новый клиент не становится клиентом банка без идентификации в отделении. |
| N10 | Целевая доступность интернет-банка 99,9% при отказе одного ЦОД. Сейчас монолит стоит на одной группе серверов, на резервный ЦОД переключаются вручную. |

### **Решение**

Диаграммы: `c4-kontekst-depozit-mvp.drawio` и `c4-konteynery-depozit-mvp.drawio`.

Сайт и веб-приложение интернет-банка читают ставки и создают заявки по HTTPS в сервисе открытия депозитов. Сервис на ASP.NET Core и своей MS SQL пишет команда интернет-банка. Монолит .NET Framework 4.5 и его база остаются для платежей и текущих счетов: Kafka в эту платформу не встаёт, а ядро с модулем СМС меняет подрядчик. СМС-код проверяет сервис и отправляет его в действующий шлюз.

Заявка и запрос особой ставки уходят в Kafka. Java-адаптер команды АБС читает очередь и вызывает процедуры Oracle с ограниченным потоком. Ставки и статусы возвращаются из outbox тем же путём. Прямой записи каналов в базу АБС нет. В Delphi депозитный и кредитный бэк-офис работают в разных разделах. После подтверждения PL/SQL открывает депозит.

Сайт на PHP и React.js ходит в сервис со своего backend. Кол-центр на Java принимает лид и возвращает запрос особой ставки. Эту доработку делает подрядчик кол-центра вместе с Java-специалистами команды АБС. Шлюз СМС остаётся прежним, его по-прежнему сопровождает IT банка.

### **Альтернативы**

Прямой доступ к Oracle или синхронный API АБС повторил бы текущие платежи. База АБС перегружена и масштабируется только вертикально, а интернет-банку запрещено вызывать API АБС в новом процессе.

Вся логика внутри монолита ASP.NET MVC 4.5 оставила бы каталог ставок рядом со справочниками, которые уже отвечают дольше секунды, и упёрлась бы в подрядчика на модуле СМС.

Сервис на Java и Spring Boot ближе команде АБС и кол-центру. Страницы интернет-банка и СМС-код выпускает команда интернет-банка на C#, поэтому Java оставлен только адаптеру.

Ставки в Excel не дают сайту и интернет-банку актуальную витрину в течение дня.

**Недостатки, ограничения, риски**

Ставка на экране отстаёт от сетки в АБС, пока сообщение не прошло через outbox. Обязательной она становится после подтверждения менеджера.

Сбой адаптера задерживает очередь. Заявка при этом уже сохранена в MS SQL сервиса. Поток процедур в Oracle нужно ограничивать.

Kafka для банка новая в сопровождении. На старте три темы: заявки, ставки, статусы.

Несколько экземпляров закрывают доступность сервиса. Само веб-приложение интернет-банка остаётся на одной группе серверов с ручным переключением на резервный ЦОД.

Срок приёма лида зависит от подрядчика кол-центра. До появления метода сервис хранит заявку и повторяет вызов.

Общий справочник ставок в АБС откроет кредитному сотруднику депозитные данные, если роли в Delphi и процедурах не разделить.
