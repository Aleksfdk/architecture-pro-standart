### **Нефункциональные требования**

| **№** | **Требование** |
| :-: | :- |
| N1 | Кол-центр банка и партнёр не обращаются к API и базе АБС. Каталог для консультации берётся из витрины сервиса открытия депозитов. |
| N2 | Карточка ставок в кол-центре банка отвечает из витрины быстрее чем за секунду. Если сервис недоступен, оператор видит последний каталог и его время. |
| N3 | Партнёр получает ставки только файлом со SFTP банка. API сервиса ему не открывается. Учётная запись читает один каталог и входит по ключу. |
| N4 | Ответ API и файл содержат публичный каталог: продукт, срок, границы суммы, базовую ставку и время среза. Клиентских данных и персональной ставки там нет. |
| N5 | Сбой SFTP или задержка файла не удаляет заявку и не отменяет подтверждение депозита в АБС. |
| N6 | Смена ставки не требует выпуска новой версии канала или системы кол-центра. |
| N7 | Файл на SFTP пишет один публикатор. Несколько экземпляров сервиса не выкладывают два разных каталога. |
| N8 | Экран кол-центра банка делает подрядчик вместе с Java-специалистами команды АБС. API и файл пишет команда интернет-банка. SFTP сопровождает IT банка. |
| N9 | Партнёр не согласует особые условия и не получает клиентские данные банка. |
| N10 | Оба кол-центра видят актуальный каталог до маркетинговой кампании. |

### **Решение**

Диаграммы: `c4-kontekst-stavki-kc.drawio` и `c4-komponenty-stavki-kc.drawio`. На них только передача ставок. Заявки, СМС и открытие депозита остаются в архитектуре MVP и здесь не повторяются.

Источник каталога тот же, что у сайта и интернет-банка. Депозитный и кредитный бэк-офис ведут сетку и риск в разных разделах АБС. АБС публикует базовый каталог в сервис открытия депозитов. Сервис на ASP.NET Core хранит витрину в своей MS SQL.

Кол-центр банка стоит в инфраструктуре банка, его бэкенд на Java. Карточка оператора читает витрину по HTTPS. В Oracle и в API АБС этот вызов не идёт. Последний успешный каталог система кол-центра держит у себя в PostgreSQL и показывает время среза, если сервис не ответил.

Партнёр — другая компания и внешняя система. API он не вызывает. Сервис выкладывает тот же публичный каталог файлом на SFTP банка. Система партнёра забирает файл по расписанию. SFTP здесь файловый канал, не вызов API сервиса. Файл пишется целиком и затем заменяет предыдущий, чтобы партнёр не прочитал обрезанный каталог.

Персональная ставка и особые условия в этот контур не входят. Их по-прежнему подтверждает депозитный бэк-офис в АБС. Оператор по телефону называет базовую ставку как предложение.

Крупные задачи по системам этого решения собраны в `zadachi.md`. Порядок работ на шесть месяцев и цель года — в `roadmap-mvp.drawio`.

### **Альтернативы**

Прямое чтение Oracle или API АБС из обоих кол-центров повторило бы нагрузку на базу, которая масштабируется только вертикально. Партнёр к тому же находится вне банка.

Excel и почта оставляют каталог с суточной задержкой. В таком письме легко уехать данным кредитного раздела.

Вызов того же HTTPS API со стороны партнёра открыл бы внутренний сервис внешней компании. Партнёр API не вызывает и готов принимать файл.

Отдельная тема Kafka наружу партнёру расширяет очередь, которую банк только начинает сопровождать. Для справочника ставок партнёру достаточно файла.

Ставки внутри скрипта, который бизнес-представитель передаёт вручную, не обновятся в течение дня. На кампании оператор прочитает прежнюю ставку.

**Недостатки, ограничения, риски**

Файл партнёра отстаёт от витрины на цикл забора. Оператор обязан видеть время файла. Обязательной ставка становится после подтверждения в АБС, а не в момент звонка.

Сбой публикатора или SFTP оставляет на сервере предыдущий файл. Заявки и открытие депозита от этого не останавливаются, но консультация идёт по старому срезу.

Два экземпляра сервиса выложат разные файлы, если публикатор не закреплён за одним писателем.

Ошибка состава файла или ответа API отдаст партнёру персональную ставку, телефон или данные кредитного раздела. В каталог для кол-центров входит только публичная сетка.

Экран кол-центра банка зависит от подрядчика. До его появления витрина уже есть у сервиса, но оператор её не видит.

Кэш в PostgreSQL при долгой недоступности сервиса показывает устаревший каталог. Без времени на карточке оператор примет его за текущий.

Передача ставок не переключает сами звонки на партнёра. Телефонная маршрутизация в ландшафте банка не описана и в это решение не входит.

Кампанию нельзя начинать раньше карточки ставок в кол-центре банка и первого файла у партнёра. Иначе звонки пойдут в системы, где ставки ещё нет.
